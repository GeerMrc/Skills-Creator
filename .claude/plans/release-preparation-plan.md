### 3.2 Git 分支管理规范（P1 - 重要）

根据用户确认，描述当前实际情况（main + feature/* 简化结构）。

```markdown
## Git 分支管理规范

### 当前分支策略
```
main (生产分支)
  │
  └─ feature/* (功能分支)
      ├─ feature/init-skill-tool
      ├─ feature/your-feature-name
      └── ...
```

### 分支命名规范
- `feature/功能描述` - 新功能开发
- `fix/问题描述` - Bug 修复
- `hotfix/紧急问题` - 生产环境紧急修复
- `refactor/重构描述` - 代码重构
- `docs/文档更新` - 文档更新
- `test/测试相关` - 测试相关

### 分支操作规范
1. **从 main 创建功能分支**（当前实际做法）
2. **开发完成后推送到远程**
3. **创建 Pull Request 到 main**
4. **Code Review 通过后合并**
5. **使用 Squash and Merge 保持提交历史整洁**
6. **合并后删除功能分支**

### Commit 规范（中英文都支持）

采用 **Conventional Commits** 格式：

**英文格式**（推荐，与国际项目一致）:
```
feat(tools): add init_skill tool implementation
fix(validators): handle edge case in skill name validation
docs(readme): update installation instructions
```

**中文格式**（与计划文档一致）:
```
feat(工具): 添加 init_skill 工具实现
fix(验证器): 处理技能名称验证的边界情况
docs(文档): 更新安装说明
```

**Type 类型**:
- `feat` - 新功能
- `fix` - Bug 修复
- `docs` - 文档更新
- `style` - 代码格式
- `refactor` - 重构
- `test` - 测试相关
- `chore` - 构建过程或辅助工具变动
```

### 3.3 禁止行为清单（P0 - 核心）

```markdown
## 禁止行为清单

### 高危操作（严格禁止）
- ❌ **禁止虚假审核** - 所有代码审查必须真实执行
- ❌ **禁止跨流程开发** - 必须按规范流程逐步执行
- ❌ **禁止高危命令执行** - 如 `rm -rf`、`dd`、`mkfs` 等
- ❌ **禁止绕过测试直接提交** - 所有代码必须通过测试
- ❌ **禁止直接修改 main 分支** - 必须通过 PR 流程

### 命令执行安全规范

**✅ 安全操作**:
```bash
ls -la /path/to/directory          # 查看目录内容
cat file.txt                        # 读取文件内容
git status                          # 查看 git 状态
git diff                            # 查看变更
rm /path/to/specific/file           # 删除单个文件
rm -r /path/to/directory            # 递归删除（需要 cd 到指定目录）
```

**❌ 危险操作（严格禁止）**:
```bash
rm -rf /                            # 根目录递归删除（系统崩溃）
rm -rf ~/important-data             # 递归删除重要目录
dd if=/dev/zero of=/dev/sda         # 磁盘覆盖（数据丢失）
:(){ :|:& };:                       # Fork 炸弹（系统崩溃）
mv * /dev/null                      # 批量删除（危险）
```

**安全替代方案**:
- 使用 `rm -r` 代替 `rm -rf`（递归删除但无强制）
- 删除前先 `ls` 确认目录内容
- 使用 `--interactive` 或 `-i` 参数
- 考虑使用 `trash` 命令代替 `rm`

### 开发行为规范
- ❌ **禁止盲目创建文档/目录** - 优先查看目录文档情况
- ❌ **禁止未经规划的新增文件** - 必须在计划中说明
- ❌ **禁止绕过 Code Review** - 所有代码必须经过审查
- ❌ **禁止破坏性重构** - 必须保持向后兼容或提供迁移指南
```

```markdown
## 任务追踪/项目目录管理/文档更新规范

### 任务追踪规范
1. **使用 TODO 清单** - 复杂任务必须创建 TODO 清单
2. **实时更新状态** - 每个步骤完成后立即更新
3. **记录阻塞问题** - 遇到问题及时记录并寻求帮助
4. **定期回顾进度** - 每日或每阶段结束时回顾

### 项目目录管理规范
1. **禁止盲目创建文档** - 创建新文档前检查现有结构
2. **优先查看目录文档情况** - 使用 `ls` 和 `cat` 了解现状
3. **遵循现有目录结构** - 不随意改变项目组织方式
4. **保持文档同步** - 代码变更时同步更新文档

### 文档更新规范
1. **以条理清晰的迭代式更新** - 分批次、有逻辑地更新文档
2. **推进项目进度追踪** - 每个文档更新都应服务于项目目标
3. **保持文档一致性** - 确保跨文档引用的准确性
4. **定期文档审计** - 每个版本发布前进行全面文档检查

### 文档创建流程
1. **检查现有文档** - 使用 `ls` 和 `cat` 了解目录现状
2. **评估必要性** - 确认新文档是否确实需要
3. **规划内容结构** - 列出新文档的章节和大纲
4. **逐步填充内容** - 按逻辑顺序逐步填充，避免一次性大量内容
5. **同步更新引用** - 更新其他文档中对新文档的引用
