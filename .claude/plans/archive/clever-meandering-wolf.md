## 一、背景与问题分析

### 1.1 当前流程概述

当前 `CLAUDE.md` 定义的七步法开发流程：

```
步骤1: 制定开发计划 → .claude/plans/feat-xxx.md
步骤2: 拆分任务清单 → TodoWrite 工具
步骤3: 执行开发工作 → 编码 + 测试
步骤4: 测试验证 → pytest --cov
步骤5: 交叉验证 → 对照计划检查
步骤6: 更新文档 → CHANGELOG.md
步骤7: 阶段性审计 → 归档计划
```

### 1.2 识别的关键问题

#### 问题1: 缺少前置任务审核机制

**现状**:
- 直接进入步骤1制定新计划
- 未验证前置阶段任务是否100%完成
- 未确认是否在正确的Git分支上

**风险**:
- 前置任务未完成导致的基础不牢固
- 在错误的分支上进行开发
- 任务间的依赖关系未被正确处理

#### 问题2: TODO任务动态管理不完善

**现状**:
- 步骤5交叉验证发现不规范/未完成任务时
- 缺少规范的回退和重新执行流程
- TODO状态更新机制不明确

**风险**:
- 未完成任务被错误标记为已完成
- 发现问题后没有规范的补救流程
- 质量控制环节失效

#### 问题3: TODO任务数量无限制

**现状**:
- 单个TODO窗口任务数量无上限
- 随着对话执行步骤增加，上下文窗口占用递增
- AI编程准确性随上下文增加而下降

**风险**:
- 任务过多导致执行准确性下降
- 上下文窗口占用过高
- 无法保证每个任务的质量

#### 问题4: 任务编号动态混乱

**现状**:
- TODO执行过程中编号会动态变更
- 完成顺序与编号顺序不一致
- 用户体验混乱

**示例问题**:
```
✔ #5 提交未跟踪的变更
✔ #8 测试验证和质量检查
✔ #1 更新 README.md 版本和统计数据
```

**风险**:
- 任务追踪困难
- 无法清晰了解执行进度
- 汇总时难以核对

#### 问题5: Git Commit规范不明确

**现状**:
- 步骤6直接进入文档更新
- 缺少独立的Git Commit步骤
- 阶段性代码变更未及时提交

**风险**:
- 代码变更未及时版本控制
- 丢失阶段性工作成果
- 无法回滚到特定阶段

#### 问题6: 阶段性汇报时机不明确

**现状**:
- 步骤7定义为"阶段性审计"
- 实际汇报应该发生在所有开发完成后
- 缺少明确的汇报时机

**风险**:
- 汇报时机混乱
- 开发工作未完成就进行汇报
- 汇报内容不完整

## 二、优化方案设计

### 2.1 新增步骤0: 前置任务审核

#### 目标
确保新任务开始前，前置阶段任务已100%完成，并且在正确的Git分支上。

#### 检查清单

```markdown
## 步骤 0: 前置任务审核 ✨ NEW

**目的**: 确保在正确的起点开始新任务开发

**检查项**:

### 0.1 前置任务完成度审核
- [ ] 检查前一阶段计划状态（应为completed）
- [ ] 验证前一阶段所有TODO均已标记为completed
- [ ] 确认前一阶段文档已归档到 `.claude/plans/archive/`
- [ ] 验证前一阶段代码已提交到Git

### 0.2 Git环境确认
- [ ] 确认当前分支（应基于develop或main创建feature分支）
- [ ] 验证本地代码与远程同步
- [ ] 确认无未提交的变更（或已stashed）
- [ ] 验证分支命名符合规范

### 0.3 前置问题处理
**如果发现未完成任务**:
1. 暂停新任务开发
2. 重新激活前一阶段计划
3. 按优先级完成未完成任务
4. 重新执行步骤0审核

**输出**:
- 前置任务审核报告（通过/不通过）
- 当前Git分支确认
- 前置问题处理方案（如有）
```

### 2.2 TODO任务动态管理机制

#### 2.2.1 TODO回退机制

当步骤5交叉验证发现问题时：

```markdown
## TODO回退机制

### 触发条件
- 步骤5交叉验证发现未完成任务
- 发现不规范的开发行为
- 测试未通过需要修复

### 回退流程
1. **问题记录**: 在当前计划中记录发现的问题
2. **TODO更新**: 将相关任务状态从 `completed` 回退到 `in_progress` 或 `pending`
3. **优先级调整**: 根据问题严重程度调整任务优先级
4. **重新执行**: 按新的优先级重新执行任务
5. **再次验证**: 完成后重新执行步骤5

### TODO状态流转
```
pending → in_progress → completed
  ↑                           ↓
  └──── 未完成/不规范 ────────┘
        (回退到 pending 或 in_progress)
```

### 示例
```markdown
## 步骤5交叉验证结果

### 发现问题
- [x] 功能1 - 已完成
- [ ] 功能2 - ❌ 测试未通过，回退到 in_progress
- [ ] 功能3 - ❌ 代码不规范，回退到 in_progress
- [x] 功能4 - 已完成

### 处理方案
1. 功能2: 修复测试用例，重新执行步骤3-4
2. 功能3: 按规范重构代码，重新执行步骤3-4
3. 完成后重新执行步骤5验证
```
```

#### 2.2.2 TODO动态更新规范

```markdown
## TODO动态更新规范

### 更新时机
1. 每完成一个任务立即更新状态
2. 交叉验证发现问题时立即回退状态
3. 新增任务时添加到TODO清单末尾

### 更新原则
- **原子性**: 每次只更新一个任务的状态
- **及时性**: 状态变更后立即更新TODO
- **准确性**: 确保TODO状态反映实际进度

### 更新示例
```python
# 原始TODO
TodoWrite(
    todos=[
        {"content": "功能1", "status": "completed"},
        {"content": "功能2", "status": "in_progress"},
        {"content": "功能3", "status": "pending"}
    ]
)

# 发现功能2有问题，回退状态
TodoWrite(
    todos=[
        {"content": "功能1", "status": "completed"},
        {"content": "功能2 - [修复中] 测试未通过", "status": "in_progress"},
        {"content": "功能3", "status": "pending"},
        {"content": "功能2.1 - 修复测试用例", "status": "pending"}  # 新增子任务
    ]
)
```
```

### 2.3 TODO任务数量限制

#### 推荐方案

```markdown
## TODO任务数量限制

### 数量范围
- **最少**: 3个任务/批次
- **推荐**: 5个任务/批次
- **最多**: 10个任务/批次

### 分批原则
1. **优先级分组**: 按P0/P1/P2优先级分批
2. **依赖关系**: 有依赖的任务放在同一批
3. **功能完整性**: 单个功能的所有任务尽量放在同一批

### 分批策略
```
批次1: 核心功能 (3-5个任务)
  ├─ 任务1: P0 核心功能实现
  ├─ 任务2: P0 核心功能测试
  └─ 任务3: P0 核心功能文档

批次2: 扩展功能 (3-5个任务)
  ├─ 任务4: P1 扩展功能实现
  ├─ 任务5: P1 扩展功能测试
  └─ 任务6: P1 扩展功能文档

批次3: 优化改进 (2-5个任务)
  ├─ 任务7: P2 性能优化
  └─ 任务8: P2 代码重构
```

### 超过10个任务的处理
当计划任务超过10个时：
1. **拆分计划**: 将大计划拆分为多个小计划
2. **设置里程碑**: 每个批次完成后设置里程碑
3. **阶段验收**: 每个批次完成后执行步骤5-7

### 示例
```markdown
# 原计划: 15个任务
## 计划A: 核心功能开发 (批次1, 5个任务)
- [ ] 任务1-5

## 计划B: 扩展功能开发 (批次2, 5个任务)
- [ ] 任务6-10

## 计划C: 优化和文档 (批次3, 5个任务)
- [ ] 任务11-15
```
```

### 2.4 任务编号管理优化

#### 问题分析

当前TODO编号混乱的原因：
1. 完成顺序与编号顺序不一致
2. 动态新增任务导致编号重排
3. 跨批次任务编号延续问题

#### 优化方案

```markdown
## 任务编号管理优化

### 方案1: 批次-序号编码
```
格式: {批次号}-{序号}

示例:
批次1:
  1-1: 制定开发计划
  1-2: 创建任务清单
  1-3: 执行核心开发

批次2:
  2-1: 编写测试用例
  2-2: 执行测试验证
  2-3: 修复发现的问题
```

### 方案2: 语义化分组
```
格式: {阶段}.{类别}-{序号}

示例:
规划阶段:
  PL-01: 制定开发计划
  PL-02: 拆分任务清单

开发阶段:
  DEV-01: 实现功能A
  DEV-02: 实现功能B

测试阶段:
  TEST-01: 编写测试用例
  TEST-02: 执行测试验证
```

### 方案3: 稳定编号 (推荐) ⭐
```
原则: 编号在创建时确定，不再变更

实现:
1. 使用日期+序号: 20260126-01, 20260126-02
2. 使用UUID短码: a1b2c3, d4e5f6
3. 使用哈希编码: task-abc123

优势:
- 编号稳定，不会因任务增减而变化
- 支持动态添加任务
- 便于跨批次引用
```

### 推荐实现
```python
# 使用日期+序号方案
import datetime

def generate_task_id():
    date = datetime.datetime.now().strftime("%Y%m%d")
    # 查找当天已有任务数
    existing_count = count_tasks_for_date(date)
    return f"{date}-{existing_count + 1:02d}"

# 示例
# 20260126-01: 制定开发计划
# 20260126-02: 创建任务清单
# 20260126-03: 执行核心开发

### 2.5 Git Commit规范步骤

#### 新增步骤6: Git提交

```markdown
## 步骤 6: Git提交 ✨ NEW

**目的**: 确保阶段性代码变更及时版本控制

### 6.1 提交前检查
- [ ] 代码通过所有测试 (`pytest --cov`)
- [ ] 代码通过质量检查 (`ruff`, `mypy`)
- [ ] 文档已同步更新
- [ ] 无敏感信息泄露

### 6.2 提交规范

#### Commit信息格式
```
<type>(<scope>): <subject>

<body>

<footer>
```

#### Type类型
- `feat`: 新功能
- `fix`: Bug修复
- `docs`: 文档更新
- `refactor`: 代码重构
- `test`: 测试相关
- `chore`: 构建/辅助工具

#### 示例
```
feat(工具): 添加批量验证功能

实现批量验证多个Agent-Skill的功能。
- 支持并发控制，默认最多5个并发
- 使用Progress bar显示进度
- 返回详细的验证结果报告

测试: 新增8个测试用例，覆盖率95%

Closes #123
```

### 6.3 提交流程
```bash
# 1. 查看变更
git status
git diff

# 2. 暂存相关文件
git add <相关文件>

# 3. 提交变更
git commit -m "feat(scope): description"

# 4. 推送到远程
git push

# 5. 创建PR (如果是功能分支)
gh pr create --title "feat: description" --body "..."
```

### 6.4 提交频率
- **原子提交**: 每个功能点完成后立即提交
- **阶段提交**: 每个批次完成后进行一次总结提交
- **发布提交**: 版本发布时创建tag和release

### 输出
- Git提交记录
- Pull Request (如需要)
- 提交哈希值记录
```
