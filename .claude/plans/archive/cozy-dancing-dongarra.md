# 计划管理流程规范化改进计划

**计划类型**: 流程规范化
**创建日期**: 2026-01-27
**优先级**: P0 (流程规范)
**基于**: 用户反馈 - 计划归档时机规范化需求

---

## 一、问题背景

### 当前问题

在实际项目开发过程中，存在以下不规范现象：

1. **提前归档**: 计划中包含P0/P1/P2/P3任务，但只执行了P1或P1+P2就直接归档
2. **状态不透明**: 未完成的任务没有明确的进度追踪机制
3. **追溯困难**: 阶段性工作缺少commit记录，无法追溯具体做了什么
4. **边界模糊**: 何时可以归档、何时不可以归档，规范不明确

### 用户要求

**归档条件**:
- ✅ 方案1: 计划中所有任务（P0+P1+P2+P3）全部完成
- ✅ 方案2: 用户明确同意归档（即使有未完成任务）

**进度追踪**:
- 阶段性执行时优先更新计划中的任务状态
- 每次更新已完成工作必须有commit记录
- 强制要求规范化更新与归档

## 二、改进方案

### 2.1 计划状态管理规范

#### 状态定义（扩展）

```
planning → in_progress → partially_completed → completed → archived
    ↑           ↑              ↑                    ↑
    └──────────┴──────────────┴────────────────────┘
              (状态可回退，需记录原因)
```

**状态说明**:

| 状态 | 含义 | 进入条件 | 可执行操作 |
|------|------|----------|------------|
| `planning` | 规划中 | 计划创建 | 编辑计划内容 |
| `in_progress` | 执行中 | 开始执行第一个任务 | 更新任务状态、提交commit |
| `partially_completed` | 阶段性完成 | P0+P1任务完成 | 更新计划状态、提交阶段性报告、**不可归档** |
| `completed` | 全部完成 | 所有任务完成或用户同意 | 执行九步法步骤6-9 |
| `archived` | 已归档 | 完成步骤9 | 只读，不可修改 |

#### 归档条件（强制）

**条件1: 全部完成**
```
所有任务状态 = completed
AND
所有验收标准满足
AND
代码已通过测试验证
```

**条件2: 用户明确同意**
```
P0+P1任务完成
AND
用户明确同意归档未完成的计划
AND
未完成任务已迁移到新计划
AND
原计划包含完整的追溯记录
```

### 2.2 进度追踪机制

#### 任务状态更新规范

**每次任务完成必须执行**:
1. 更新计划文档中的任务状态
2. 更新TodoWrite中的任务状态
3. 提交Git commit（规范格式）
4. （可选）生成阶段性进度报告

#### Commit规范（强制性）

**格式**:
```
chore(plan): 更新计划进度 - [计划名称]

完成工作:
- [任务ID] 任务描述 (状态: completed)
- [任务ID] 任务描述 (状态: completed)

变更文件:
- .claude/plans/[计划名称].md

任务完成进度: X/Y (Z%)
下一阶段: [下一阶段任务描述]
```

**示例**:
```
chore(plan): 更新P3阶段优化任务进度

完成工作:
- T-301 清理__pycache__ (状态: completed)
- T-302 测试覆盖率缺口分析 (状态: in_progress)

变更文件:
- .claude/plans/jolly-exploring-pinwheel.md

任务完成进度: 1/2 (50%)
下一阶段: 继续执行T-302覆盖率缺口分析
```

### 2.3 计划文档更新规范

#### 计划文档必须包含

**1. 任务清单表格**:
```markdown
## 任务清单

| 任务ID | 任务名称 | 优先级 | 预计时间 | 执行状态 | 完成时间 | Commit |
|--------|----------|--------|----------|----------|----------|--------|
| T-001 | 任务描述 | P0 | 30分钟 | completed | 2026-01-27 | abc123 |
| T-002 | 任务描述 | P1 | 1小时 | in_progress | - | - |
| T-003 | 任务描述 | P2 | 2小时 | pending | - | - |
```

**2. 进度追踪区域**:
```markdown
## 执行进度

**当前状态**: in_progress
**开始时间**: 2026-01-27
**最后更新**: 2026-01-27 14:30

**任务完成情况**:
- P0: 1/1 (100%) ✅
- P1: 3/3 (100%) ✅
- P2: 2/5 (40%) ⚠️
- P3: 0/3 (0%) ⏸️

**总体进度**: 6/12 (50%)

**最近更新**:
- [2026-01-27 14:30] T-004完成，commit: def456
- [2026-01-27 13:00] T-003完成，commit: abc123
```

**3. 归档检查清单**:
```markdown
## 归档检查清单

### 必须达成（全部完成才能归档）
- [ ] P0-001: 任务描述
- [ ] P1-001: 任务描述
- [ ] P1-002: 任务描述
- [ ] P2-001: 任务描述
- [ ] P2-002: 任务描述

### 可选（用户同意可跳过）
- [ ] P3-001: 任务描述 (用户同意跳过: 2026-01-27)
- [ ] P3-002: 任务描述 (迁移到新计划: feat-xxx.md)
```

### 2.4 未完成任务处理机制

#### 机制1: 迁移到新计划

**适用场景**: P2/P3任务需要延期但不阻塞当前计划归档

**流程**:
1. 在原计划中标记任务状态为 `migrated`
2. 创建新计划，包含迁移的任务
3. 在新计划中引用原计划（追溯关系）
4. 用户明确同意后归档原计划

**示例**:
```markdown
# 原计划
| T-008 | 清理__pycache__ | P3 | 5分钟 | migrated | - | - |

> 注: 迁移到 [新计划](.claude/plans/feat-cleanup.md)，追溯ID: TR-2026-01-27-001

# 新计划
## 相关计划
- 前置计划: [.claude/plans/old-plan.md](.claude/plans/old-plan.md)
- 追溯ID: TR-2026-01-27-001
```

#### 机制2: 用户同意归档

**适用场景**: 低优先级任务决定不再执行

**流程**:
1. 在计划中标记任务状态为 `cancelled`
2. 记录取消原因和用户同意时间
3. 在归档报告中说明
4. 用户明确确认后归档

**示例**:
```markdown
| T-009 | 优化资源URI | P3 | 2小时 | cancelled | - | - |

> 取消原因: 当前格式已符合MCP标准，无需优化
> 用户同意: 2026-01-27
```
